#+DATE: <2026-11-08 Sun>

2026 年 4 月 28 日，我在一个容器里启动了一个 agent。从那天起它一直在运行，没有人盯着。它叫
overlord。它读我的邮件和 Signal 消息，维护一个知识库，在任务看板上领活、写代码、自己合并 PR。
到今天，它已经往自己的仓库里提交了 3,500 多次。

这篇文章讲它是怎么搭起来的。整个系统只有三块：

1. 核心：容器里的 cron、消息总线和 Claude Code CLI。
2. 大脑：一个由 LLM 维护的 wiki。
3. 通道：邮件和 Signal。

三块背后有同一个设计原则：重复的活交给确定性脚本，大模型只做需要判断的事。这一点我单独写一节。

* 核心：cron、消息总线、Claude Code CLI

三样东西都装在一个 podman 容器里。

*cron* 负责"什么时候跑"。我写了一个小调度器，也叫 overlord。它按 cron 表达式启动 job。job
就是一个普通脚本，跑完就退出。现在一共只有 7 个 job：

- ~gmail-check~：每分钟查一次收件箱。
- ~signal-check~：每分钟查一次 Signal。
- ~gmail-safety-net~：每小时把还没处理的邮件再报一次。
- ~auth-watchdog~：每 10 分钟检查登录是否过期。
- ~daily-maintenance~：每天清理磁盘和日志。
- ~prompt-dispatcher~：每 10 分钟检查哪些定时任务到期了。
- ~overlord~：每分钟检查一次有没有发给它的消息，有就调用 Claude。

前六个都是确定性的小脚本，不调用大模型。它们是传感器和路由器。

*消息总线*负责"跑什么"。每个 job 结束时往标准输出写一个 JSON：

#+begin_src json
{"consumer": "overlord", "message": "..."}
#+end_src

~consumer~ 是收件人。调度器把这条消息存下来。声明了 ~--consumes overlord~ 的 job 只在有未消费
消息时才启动，并从标准输入拿到这些消息。所以 ~gmail-check~ 发现新邮件时，不直接处理。它只发一条
消息给 ~overlord~。

*Claude Code CLI* 负责"怎么做"。~overlord~ 这个 job 拿到消息后，运行一次无头的
~claude -p~，把消息作为提示词交给它。Claude 在容器里有 shell，能读写文件、跑测试、调用 ~gh~ 和
Gmail API。一次运行最多一小时。

这里有一个我很喜欢的性质：失败不丢活。如果一次 Claude 运行失败了，它的消息不会被标记为已消费。
下一分钟调度器会用同一条消息再启动一次。网络断了、API 返回 500、登录过期，都只是推迟，不会丢失。

** Claude 用 cron 和总线自己调度自己

这是整个设计的关键。cron 和总线不只是我用来调度 Claude 的工具，Claude 自己也用它们。它有三种
方式：

- *定时提示词。* 新的周期性工作不写成 job，而是写成一条英文提示词，加一个 cron 表达式，存在
  ~scheduled-prompts.json~ 里。~prompt-dispatcher~ 到点就把它发给 ~overlord~。每日新闻摘要、每日
  测验、晚间总结、开发队列，都是这样跑的。现在有 14 条。Claude 想要一个新的定时任务时，自己往这个
  文件里加一条就行。
- *交接便条。* 一次运行结束时，如果活没干完，Claude 写一句 ~--what-next~。这句话会作为一条新
  消息发给 ~overlord~，下一分钟的运行就会接着干。下一次运行不记得上一次，便条就是它们之间唯一的
  联系。
- *直接发消息。* 任何地方都可以用 ~overlord send~ 往总线投一条消息。~signal-check~ 遇到需要
  动手的请求时，就是这样把它升级给 ~overlord~ 的。

所以 Claude 既是消费者，也是生产者。它决定自己下一次什么时候醒、醒来做什么。

所有消息都排在同一个队列里，一次只跑一个。这很慢，但简单。两个运行永远不会同时改同一个文件。

* 设计重点：重复的活交给确定性脚本

这是我最想强调的一点。凡是每次都一模一样的步骤，都写成脚本，不交给大模型。

最明显的例子是那六个 job。~gmail-check~ 每分钟跑一次，一天 1,440 次，绝大多数时候收件箱是空的。
如果每次都叫醒 Claude 去看一眼，就是一天一千多次白白的调用。现在它是一个小脚本，几秒钟跑完，不花
一个 token。只有真的来了信，它才发消息给 ~overlord~。

定时提示词里也是一样。提示词负责判断和写作，收集材料的部分交给脚本：

- *每晚总结。* ~daily-wrapup.py~ 负责把当天的邮件、Signal 和 git 提交收集好。Claude 只负责读
  这些材料、写总结。
- *教训提取。* 这条提示词几乎只有一句话：运行 ~_run_lessons.py~，把它的输出原样转发。
- *发件人判断。* 一封信是不是我发的，由 ~gmail_sender.py~ 检查地址和 DKIM、DMARC 签名后决定，
  不让模型自己判断。信里写什么都改变不了这个结论。

这样做有四个好处：

- *省钱。* 脚本不消耗 token。
- *快。* 脚本几秒钟跑完，不占用那一个共享的队列。
- *可测试。* 脚本有单元测试，同样的输入永远得到同样的输出。
- *错得明显。* 脚本出错会打出一个堆栈，而模型出错时，往往给出一个看起来很合理的错误答案。

这些脚本大多是 Claude 自己写的。它发现自己在好几次运行里重复同样的几步时，就把这几步写成一个
Python 脚本，加上测试，提交到仓库。下一次运行直接调用脚本。我给它的规则只有一条：只要逻辑稍微
复杂一点，就写成仓库里的 Python 脚本，不要塞进提示词，也不要写成一长串 shell。

* 大脑：LLM wiki

Claude 每次运行都从零开始，没有记忆。所以记忆必须放在文件里。

我用的是 Karpathy 提出的 LLM Wiki 模式。仓库里有一个 ~kb/~ 目录：

- ~kb/sources/~：原始材料，进来以后不再修改。现在有 191 份，包括论文、每日总结邮件、我的 Signal
  记录。
- ~kb/wiki/~：由 Claude 维护的页面。现在有 480 多页，分为概念、实体、比较和综合。
- ~kb/SCHEMA.md~：页面的格式和规则。

新材料进来时，Claude 不是简单地存一份。它读完材料，更新所有相关的页面，加上互相之间的链接，并
标出和旧页面矛盾的地方。查询时，它先读 wiki，再回答。

除了 wiki，还有两样东西帮它记事：

- *记忆文件。* ~memory/~ 下有 122 个小文件，每个记一件事。大部分是我纠正过它的地方，以及纠正的
  原因。
- *看板。* 所有工作都是看板上的卡片。卡片有租约，一次运行崩溃了，租约到期后别的运行可以接手。

wiki 和记忆文件都在 git 里，每一个版本都留着。我认为这段历史就是它本身，好的坏的都算。

我从第一天起就没有让它"学会"什么技能。我只让它把学到的东西写进知识库。技能只决定什么时候读哪
一页。

* 通道：邮件和 Signal

我在这台机器上没有 shell。我给它的每一条指令都是一条消息，它给我的每一个结果也是一条消息。

- *邮件*用于正式的事：提需求、看报告、回答它的问题。~gmail-check~ 每分钟收一次信。只有我的地址
  能下指令。它每做完一件事都会回信。
- *Signal*用于短消息，因为它直接到我手机上。~signal-check~ 用一个更快的模型当场回复。需要真正
  动手的请求，它会发给 ~overlord~。

长文档走另一条路。Claude 把 markdown 写进仓库，我在 doc-review 里逐行评论，它再改。这篇文章也会
这样改。

* 为什么这样设计

回头看，每一个选择都是为了少一样东西：

- 没有常驻的 agent 进程。每次运行都是一个独立的 ~claude -p~，跑完就退出。
- 没有会话记忆。记忆全在 git 里的文件中。
- 没有专门的 agent 框架。调度是 cron，通信是 JSON，工具是 shell。
- 没有让模型做重复的活。能写成脚本的步骤都写成了脚本。
- 没有给我用的控制台。我只用邮件和手机。

剩下的部分小到我一个人能看懂。它在这上面已经跑了半年多。
